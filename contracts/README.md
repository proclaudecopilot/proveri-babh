## Правила за промяна (приемане на ARC-005)

1. **Промяна на договор = промяна на версия.** Добавяне на поле: minor (1.1); премахване/преименуване на поле, смяна на тип, enum или null семантика: major (2.0) с период на съвместимост и migration бележка в `CHANGES.md`.
2. **Един договор за всички потребители.** UI (`assets/babh6.js`), CSV експорт, бъдещи saved queries и watches четат същите DTO; фронтенд и бекенд промяна са в един PR с owner review (`docs/plan/ownership.yml`).
3. **Еднакви enum и null семантики.** `null` = неизвестно/няма стойност в източника; `''` = празно поле в източника; `0/1` флаговете са булеви. Датите са `YYYY-MM-DD` или `null`; никога `0000-00-00`, никога „най-стара“. Enum стойностите са изброени в схемите; невалидна стойност е грешка в contract теста.
4. **Contract тест** (ARC-005 конкретна проверка): `tests/php/contracts.test.php` валидира примерни отговори срещу схемите с минимален JSON Schema валидатор без зависимости и отхвърля невалиден enum/`status`, неочакван тип дата (d.m.Y, число), липсващи полета и година 1968. Известна дупка: `pattern` не проверява календар (`0000-00-00` минава) — версия 2.0 добавя `format: date`.
5. **Известни несъответствия в 1.0**, които се поправят само с версия 2.0 (не тихо):
   - кратки ключове (`n`, `p`, `tr`, `nd`) без provenance по поле (DAT-001, API-006);
   - `x` („липсва в последния пълен файл“) и `del` („бележка за заличаване“) са отделни, но `xd` е дата на импорта, не на източника;
   - `fc`/`f` зависят от Pro (сървърът ги нулира) — capability, а не договор;
   - `/stats` връща форматирани дати (`d.m.Y`) вместо ISO — UI ги показва директно;
   - грешките нямат `correlation_id`, `retryable`, `field_errors` (API-003);
   - няма `dataset_version`/`query_hash` в list отговорите (DAT-010, API-001).
